# 1. Technical Overview

## 1.1 Purpose

This document defines the technical architecture, development standards, file structure, functionality, performance requirements, accessibility requirements, and deployment procedures for the 16:01 Studio portfolio website.

It serves as the technical implementation specification for AI coding assistants, developers, and future maintenance.

The implementation must follow the approved Product Requirements Document (PRD).

The PRD defines what the product must accomplish. This document defines the technical requirements for implementing it.

## 1.2 Technical Objectives

The implementation must:

1. Provide a responsive portfolio website.
2. Present graphic design and illustration projects.
3. Support individual project case-study pages.
4. Provide functional navigation and project filtering.
5. Support purposeful animations and interactions.
6. Remain compatible with GitHub Pages.
7. Avoid unnecessary backend infrastructure.
8. Maintain fast loading and good accessibility.
9. Use readable, maintainable code.
10. Allow new projects to be added through a simple file-based workflow.
11. Operate without paid hosting or mandatory paid services.

## 1.3 Technical Principles

- Static-first architecture.
- Minimal dependencies.
- Semantic HTML.
- Modular CSS.
- Vanilla JavaScript for straightforward interactions.
- Reusable layouts and components.
- Progressive enhancement.
- Responsive design.
- Accessibility-first implementation.
- Performance-conscious asset management.
- Deployment-compatible file paths.

# 3. System Architecture

## 3.1 Architecture Type

The website must use a static multi-page architecture.

The browser loads HTML documents, CSS stylesheets, JavaScript files, and image assets from GitHub Pages.

JavaScript handles client-side interactions such as project filtering and mobile navigation.

No server-side processing is required for the core portfolio.

## 3.2 Architecture Diagram

```text
                   VISITOR
                      |
                      v
               WEB BROWSER
                      |
                      v
              GITHUB PAGES
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       HTML         CSS        JAVASCRIPT
          |           |           |
          v           v           v
       Content     Layouts    Interactions
          |           |           |
          +-----------+-----------+
                      |
                      v
               PORTFOLIO DISPLAY
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
        Home        Projects    Case Studies
                      |
                      v
                Contact Links
```

## 3.3 Request and Rendering Flow

1. The visitor opens the website.
2. The browser requests the relevant HTML document.
3. The document loads its required CSS, JavaScript, and assets.
4. The browser renders the page.
5. JavaScript initializes the required interactions.
6. The visitor navigates between pages or filters projects.
7. GitHub Pages serves the requested static resources.

The website must not depend on JavaScript to display its essential textual content.

Where practical, primary navigation and project links should remain functional without JavaScript.

# 4. Hosting and Deployment Configuration

## 4.1 Hosting Requirements

The website must be deployed using GitHub Pages.

**Target URL:** `https://saelvostudio.github.io/`

The implementation must account for the actual GitHub Pages repository configuration.

## 4.2 Deployment Requirements

- GitHub Pages must be enabled.
- The correct repository and publishing source must be selected.
- All required files must exist in the published directory.
- HTML pages must use valid asset paths.
- CSS and JavaScript files must load successfully.
- Internal navigation must work after deployment.
- Project pages must be accessible through direct URLs.
- No development-server-only paths may be used in production.
- No secret credentials may be included in the repository.

## 4.3 Path Management

Because GitHub Pages may serve a repository from a project subpath or from a user-site root, asset paths must match the actual deployment configuration.

For the root website `saelvostudio.github.io`, paths should be tested against the deployed structure.

Avoid assuming that paths which work locally will automatically work on GitHub Pages.

### Requirements

- Use consistent asset-path conventions.
- Verify all CSS and JavaScript references.
- Verify image paths.
- Verify project-to-project navigation.
- Avoid unnecessary hardcoded domain references.
- Test the published website rather than relying exclusively on local previews.

## 4.4 HTTPS

The deployed website must use HTTPS.

No HTTP-only external resource should be required for essential functionality.

# 6. HTML Technical Requirements

## 6.1 Document Structure

Every HTML page must include:

- HTML5 document declaration.
- Appropriate language declaration.
- Character encoding.
- Responsive viewport metadata.
- Unique page title.
- Appropriate meta description.
- Correct stylesheet references.
- Semantic page structure.
- Valid internal navigation.
- Appropriate social-sharing metadata where needed.

## 6.2 Semantic Elements

Use appropriate HTML elements, including:

- `<header>`
- `<nav>`
- `<main>`
- `<section>`
- `<article>`
- `<footer>`
- `<figure>`
- `<figcaption>`

Use buttons for actions and links for navigation.

Do not use nonsemantic elements solely to imitate the appearance of interactive controls.

## 6.3 Heading Hierarchy

- Each page should have a clear primary heading.
- Heading levels must follow a logical hierarchy.
- Headings must not be selected purely for their default visual size.
- CSS must control visual typography.

## 6.4 Image Markup

Images must:

- Include appropriate alternative text.
- Use width and height attributes or an equivalent aspect-ratio strategy.
- Preserve their intended proportions.
- Use lazy loading when appropriate.
- Avoid unnecessary loading delays for the primary hero image.

Decorative images should use empty alternative text where appropriate.

## 6.5 Link Requirements

- Links must have meaningful destinations.
- Internal links must point to existing pages or valid sections.
- External links must be verified.
- Email links must use valid `mailto:` syntax.
- Links that open new tabs must follow appropriate security practices.

# 7. CSS Technical Requirements

## 7.1 CSS Architecture

CSS must be organized by purpose.

The recommended organization is:

| File | Responsibility |
|---|---|
| `reset.css` | Consistent baseline styling |
| `variables.css` | Design tokens and global variables |
| `global.css` | Typography and global element styles |
| `components.css` | Buttons, navigation, project cards, shared UI |
| `layout.css` | Grids, containers, section layouts |
| `pages.css` | Page-specific styling |
| `responsive.css` | Responsive adjustments |

Files may be combined if the project remains easy to maintain.

## 7.2 CSS Custom Properties

Global design tokens must use CSS custom properties.

Example:

```css
:root {
  --color-background: #111310;          /* Dark background */
  --color-text: #F5F2EB;                /* Primary text/warm off-white */
  --color-dark: #111111;                /* Dark sections (maintained) */
  --color-muted: #B0ADA5;              /* Warm gray secondary text */
  --color-accent: #C64B35;             /* Burnt red accent (unchanged) */
  --color-border: #34352F;             /* Dark gray borders/divider */

  --font-display: sans-serif;
  --font-body: sans-serif;

  --container-width: 1440px;

  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-6: 1.5rem;
  --space-8: 2rem;
  --space-12: 3rem;
  --space-16: 4rem;

  --transition-fast: 180ms ease;
  --transition-normal: 300ms ease;
}
```

These values are initial defaults and may be refined during design implementation.

## 7.3 Layout Requirements

Use CSS Grid and Flexbox where appropriate.

The layout must support:

- Flexible project grids.
- Large editorial headlines.
- Responsive spacing.
- Variable image aspect ratios.
- Full-width artwork.
- Controlled content widths.
- Asymmetrical compositions.
- Consistent alignment.

Avoid fixed widths that cause overflow on smaller screens.

## 7.4 Responsive Units

Prefer responsive units where appropriate:

- `rem`
- `%`
- `vw`
- `vh`
- `svh`
- `clamp()`
- `minmax()`

Use fixed pixel values only when they are appropriate for the component.

## 7.5 Styling Rules

- Avoid excessive specificity.
- Avoid repeated overrides.
- Avoid unnecessary `!important`.
- Keep responsive rules organized.
- Maintain visible keyboard-focus states.
- Avoid layout shifts caused by late-loading assets.
- Keep the visual system consistent across pages.

# 8. JavaScript Technical Requirements

## 8.1 General Rules

JavaScript must be lightweight, readable, and limited to required interactions.

Requirements:

- Use modern browser-supported JavaScript.
- Avoid unnecessary dependencies.
- Handle missing elements safely.
- Avoid duplicate event listeners.
- Avoid global variables unless necessary.
- Separate independent interactions into suitable modules or files.
- Provide graceful behavior when optional features are unavailable.
- Avoid console errors.

## 8.2 Main JavaScript Responsibilities

### `main.js`

Responsible for shared initialization and global interactions.

### `navigation.js`

Responsible for mobile navigation behavior.

### `project-filter.js`

Responsible for filtering portfolio projects by category.

### `motion.js`

Responsible for optional scroll reveals and other motion enhancements.

These files may be combined when the implementation remains simpler and clearer.

## 8.3 Script Loading

Use deferred script loading where appropriate.

Example:

```html
<script src="js/main.js" defer></script>
```

Scripts must not unnecessarily block the initial page render.

## 8.4 Error Handling

JavaScript must not assume that every component exists on every page.

Page-specific scripts must safely handle missing elements.

Essential content must remain visible if a nonessential animation script fails.

# 9. Project Filtering Requirements

## 9.1 Functional Behavior

The portfolio must support client-side filtering.

When a visitor selects a category:

1. The selected category is identified.
2. Matching projects remain visible.
3. Other projects are hidden.
4. The layout updates correctly.
5. The All Work control restores all published projects.

## 9.2 Implementation

Filtering may use HTML data attributes.

Example:

```html
<button type="button" data-filter="all">
  All Work
</button>

<button type="button" data-filter="illustration">
  Illustration
</button>

<article
  class="project-card"
  data-category="illustration"
>
  <!-- Project content -->
</article>
```

JavaScript must implement the filtering behavior.

## 9.3 Accessibility

- Filters must be keyboard-accessible.
- Selected states must be identifiable.
- Focus indicators must be visible.
- The interface must remain usable without hover.
- Filtering must not unexpectedly move keyboard focus.

## 9.4 Performance

Filtering should work without reloading the page.

The initial implementation must not require a filtering library.

# 13. Animation and Motion Requirements

## 13.1 Permitted Techniques

Use CSS transitions and animations for simple effects.

Use JavaScript only when needed for interaction or triggering behavior.

The Intersection Observer API may be used for scroll-reveal effects.

## 13.2 Motion Requirements

- Use restrained durations.
- Avoid unnecessary simultaneous animations.
- Prevent content from becoming inaccessible during transitions.
- Avoid blocking navigation.
- Keep mobile motion lightweight.
- Avoid unnecessary layout recalculations.
- Use transform and opacity for suitable animations.

## 13.3 Reduced Motion

The website must respect the visitor's operating-system preference.

Example:

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    scroll-behavior: auto !important;
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

The implementation should also avoid JavaScript-driven motion when reduced motion is requested.

Essential functionality must remain intact.
